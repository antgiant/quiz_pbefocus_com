# Load performance

## How loading works

1. `index.html` preloads the startup JSON (`manifest.json`, `packs/index.json`, `years.json`, the practice files) and the module graph while the page is still parsing. Nothing blocks the first paint.
2. The manifest lists every chapter with a content `hash`. `packs/index.json` lists one pack per season. Both are generated by `npm run build:data` (see the README), and a GitHub Action does that on every data push.
3. When a season is first used, `DataService.loadYearPack` downloads that season's pack (one request), keeps it in IndexedDB (`pack-store.js`, one record per season, replaced when its hash changes) and fills the chapter cache. Repeat visits skip the download and read IndexedDB instead.
4. A chapter the pack does not supply (stale pack, season without a pack, "Custom - Entire Bible") is fetched on its own as `by-chapter/...json?v=<hash>`. Chapters that exist only for verse text (`questions: 0`) are never requested.
5. Big third-party files load on demand (`lazy-vendor.js`): `compromise` in the background right after startup (needed by fill-in-the-blank), JSZip and the PowerPoint template only when you download a deck. `pptxgen.min.js` is no longer loaded: nothing uses it.
6. Opening `index.html` from disk (`file://`) still works: when `fetch` is blocked the manifest loader falls back to the script bundles from `node scripts/build-local-bundle.mjs`.

Only the selected season's questions are ever loaded, so the first load does not grow as the question bank covers more of the Bible.
The exception is "Custom - Entire Bible", which can select every chapter and loads each one it needs.

## Measuring

```bash
npm run bench:fixture -- --out /tmp/site --chapters 1189   # copy of the site with a Bible-sized bank
npm run bench -- --site /tmp/site --runs 7 --net fast4g --cpu 4
```

`bench:fixture` clones real chapters into synthetic books (the real seasons and packs are untouched).
`bench` serves a directory the way GitHub Pages does (gzip, ETag, `max-age=600`) and loads it in Chromium with 4x CPU and Fast 4G throttling,
first with an empty cache ("cold") and then again with the same profile ("warm"). The verse API is answered locally after 150 ms.
It needs Playwright (`PLAYWRIGHT_PATH=<dir containing node_modules/playwright>`) and a Chromium (`PW_CHROMIUM=<binary>`).
To compare with an older version, check it out in a worktree and point `--src` at it when building the fixture.

Columns: *controls* is when the season list is filled in, *questions* when the first preview is generated,
*FCP* first contentful paint, *transfer* bytes received over the network.

## Results (median of 5-7 runs, 4x CPU, Fast 4G)

| Scenario | Before | After |
|---|---|---|
| Current data, cold: FCP | 2.4 s | 0.25 s |
| Current data, cold: controls ready | 2.7 s | 0.5 s |
| Current data, cold: first questions | 3.9 s | 2.5 s |
| Current data, cold: bytes transferred | 3.4 MB | 0.46 MB |
| Current data, warm: controls / questions | 1.1 s / 2.3 s | 0.43 s / 2.1 s |
| Current data, warm: network requests | 31 | 0 |
| Bible-sized bank, cold: FCP | 11.5 s | 0.26 s |
| Bible-sized bank, cold: controls ready | 11.8 s | 0.54 s |
| Bible-sized bank, cold: first questions | 13.2 s | 2.5 s |
| Bible-sized bank, cold: bytes transferred | 10.9 MB | 0.48 MB |
| Bible-sized bank, warm: first questions | 10.4 s | 2.2 s |
| Bible-sized bank, JS heap | 205 MB | 20 MB |
| Slow 4G, current data, cold: controls / questions | 12.1 s / 14.4 s | 1.2 s / 4.1 s |

The Bible-sized rows match the current-data rows: load time no longer depends on how many chapters exist.
What remains of the time to first questions is CPU work on a throttled core: loading and running `compromise`,
then fill-in-the-blank word scoring over the season's verses.

Where the time went before: the 1.7 MB (64 MB at Bible scale) all-questions script blocked rendering and was re-parsed on every visit,
two more blocking scripts added 1.3 MB, every chapter of the bank was loaded to work out which were selectable,
and a 404 was requested for each chapter that has verse text but no questions.
The hero and logo images were also 3 MB of PNG; they are now 120 KB of WebP.
