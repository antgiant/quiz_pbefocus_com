# Load performance

People open this app often and the questions rarely change, so everything is built around repeat visits being (nearly) free and a first visit being small.

## How loading works

1. **Nothing blocks the first paint.** `index.html` preloads the startup JSON and the module graph while the page parses.
2. **Service worker (`sw.js`).** The app files are precached as one versioned set and served cache-first, so a returning visitor does not wait on the network or on GitHub Pages' 10-minute cache.
   Season packs and chapters have their content hash in the URL and are cached for good (old ones are pruned when the manifest changes).
   The manifest and other small data files are served from cache and refreshed in the background, so new questions arrive on the next visit.
   A new app version installs in the background and takes over once every tab is closed.
   It registers over https only (or with `?sw=1`, for testing), so local development never serves stale files.
   `sw.js` is generated by `scripts/build-data.mjs` from `scripts/sw-template.js`; its version is a hash of the app files, so the Action rebuilds it on any app change.
3. **One pack per season.** `DataService.loadYearPack` downloads the active season's pack in one request and keeps it in IndexedDB (`pack-store.js`, one record per season, replaced when its hash changes).
   Packs leave out fields the app never reads (`originalIds`, `createdOn`, `updatedOn`).
   A chapter the pack does not supply is fetched as `by-chapter/...json?v=<hash>`; chapters that only exist for verse text (`questions: 0`) are never requested.
4. **Verse analysis is saved between visits.** Picking the words to blank needs the `compromise` NLP library, which is slow to load and run.
   Its output depends only on the verse text, so it is cached per verse (`blank-engine.js`) and saved in IndexedDB (`analysis-store.js`).
   After the first visit, idle time analyses the rest of the season's verses; once they are saved the library is never downloaded or run.
   Until enough is saved it downloads at startup, in parallel with the data. Word scores (TF-IDF) are computed only for verses that get blanked, and reused when settings change.
5. **Other big files load on demand** (`lazy-vendor.js`): JSZip and the PowerPoint template only when you download a deck. `pptxgen.min.js` is no longer loaded.
6. Opening `index.html` from disk (`file://`) still works through the script bundles from `node scripts/build-local-bundle.mjs`.

Only the selected season is ever loaded, so the first load does not grow as the question bank grows.
("Custom - Entire Bible" is the one mode that loads every chapter it needs; it is not optimised.)

## Measuring

```bash
npm run bench:fixture -- --out /tmp/site --chapters 31        # copy of the site (use 1189 for a Bible-sized bank)
npm run bench -- --site /tmp/site --runs 5 --sw --net fast4g --cpu 4
```

`bench` serves a directory like GitHub Pages (gzip, ETag, a short `max-age`) and loads it in Chromium with throttled CPU and network:

- **cold**: empty profile
- **warm**: second visit while the HTTP cache is fresh
- **return**: a later visit after the HTTP cache lifetime has passed, so every file needs revalidating unless the service worker answers

The first page is kept open for `--dwell` seconds (default 12) so background work, like saving verse analysis, gets its idle time. `--sw` opens the page with `?sw=1`.
The verse API is answered locally (150 ms, distinct text per chapter).
It needs Playwright (`PLAYWRIGHT_PATH=<dir containing node_modules/playwright>`) and a Chromium (`PW_CHROMIUM=<binary>`).
To compare with an older version, check it out in a worktree and point `--src` at it when building the fixture.

*controls*: the season list is filled in. *questions*: the first preview is generated. *FCP*: first contentful paint.

## Results (current data, median of 3 runs, 4x CPU)

| | Fast 4G before | Fast 4G after | Slow 4G before | Slow 4G after |
|---|---|---|---|---|
| Cold: first paint | 2.4 s | 0.24 s | 10.8 s | 0.5 s |
| Cold: controls / questions | 2.7 s / 4.3 s | 0.57 s / 2.5 s | 12.2 s / 14.8 s | 1.4 s / 4.3 s |
| Cold: data downloaded | 3.4 MB | 0.35 MB | - | 0.47 MB |
| Warm: controls / questions | 1.2 s / 2.3 s | 0.49 s / 1.1 s | 1.1 s / 3.0 s | 0.48 s / 1.1 s |
| Return visit: controls / questions | 1.2 s / 2.5 s | 0.48 s / 1.1 s | 1.7 s / 3.7 s | 0.51 s / 1.1 s |
| Return visit: network requests | 56 | 0 | 56 | 0 |

A repeat visit is now about 1.1 s to questions on a throttled CPU, with no network at all. What remains is the browser starting up, reading IndexedDB and generating the preview.
With a Bible-sized bank the numbers are the same, because only the selected season loads (an earlier run: 13.2 s to questions before, 2.5 s after).

Where the time went originally: a blocking 1.7 MB all-questions script re-parsed on every visit, two more blocking scripts, a 404 for every chapter with verse text but no questions,
every chapter loaded just to find out which were selectable, 3 MB of PNG images, and the NLP library loaded and run on every visit.
